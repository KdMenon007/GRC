
Software development controls in Annex A focus on integrating **information security throughout the software development lifecycle (SDLC)**.

The objective is to protect the **confidentiality, integrity, and availability (CIA)** of information processed by applications.

### Key security areas

|Area|What should be done|
|---|---|
|**Security development policy**|Define security rules, responsibilities, and SDLC requirements|
|**Security requirements**|Identify security requirements before development begins|
|**Secure architecture**|Define secure architecture and engineering principles|
|**Secure coding**|Apply secure programming practices|
|**Environment separation**|Separate development, testing, and production|
|**Test data**|Protect test data and avoid unnecessary use of real sensitive data|
|**Security testing**|Verify that security requirements are actually met|
|**Software acceptance**|Formally approve software before production|
|**Source code protection**|Restrict and control access to source code|
|**Change management**|Ensure software/system changes are authorized and controlled|

### 1. Security Development Policy

Create a policy that defines:

- Security responsibilities
    
- Development security requirements
    
- SDLC processes
    
- Approval requirements
    
- Testing requirements
    
- Source-code protection
    
- Change management
    

This should apply to **internal and outsourced development** where relevant.

---

### 2. Define Security Requirements Early

Security should be considered **before development starts**, rather than added at the end.

Examples:

- Authentication requirements
    
- Authorization requirements
    
- Encryption requirements
    
- Logging requirements
    
- Data protection requirements
    
- Input validation requirements
    
- Privacy requirements
    

**Security should be built into the SDLC from the beginning.**

---

### 3. Secure Architecture and Engineering

Define secure architecture principles covering different layers:

**Business → Data → Application → Technology**

Examples:

- Secure authentication
    
- Secure session management
    
- Input validation
    
- Encryption
    
- Least privilege
    
- Secure API design
    
- Protection of sensitive data
    

---

### 4. Separate Development, Testing and Production

Development and testing environments should be separated from the **operational/production environment**.

Example:

**Development → Testing → Production**

This reduces the risk of:

- Developers accidentally affecting production.
    
- Unfinished software being deployed.
    
- Test activities affecting business operations.
    
- Sensitive production information being exposed.
    

---

### 5. Protect Test Data

Test data should be carefully selected.

Avoid using real:

- Customer information
    
- Personal data
    
- Financial information
    
- Confidential business information
    

when it is not necessary.

Where appropriate, use **synthetic, anonymized, or masked data**.

---

### 6. Security Testing and Acceptance

New software should be tested against its predefined security requirements.

Examples:

- Authentication testing
    
- Authorization testing
    
- Encryption verification
    
- Input validation testing
    
- Vulnerability testing
    
- Security code review
    

Before deployment, there should be a **formal acceptance process** confirming that the required security criteria have been satisfied.

---

### 7. Protect Source Code

Access to source code should be restricted to authorized personnel.

Examples:

- Role-based access
    
- Repository permissions
    
- Strong authentication
    
- Version control
    
- Access logging
    
- Code review
    

**Principle:** Only people who need access to source code should have it.

---

### 8. Software and System Change Control

Changes to software should be:

**Requested → Assessed → Approved → Implemented → Tested → Reviewed**

Changes should be controlled so that unauthorized or unnecessary modifications do not introduce security vulnerabilities.
