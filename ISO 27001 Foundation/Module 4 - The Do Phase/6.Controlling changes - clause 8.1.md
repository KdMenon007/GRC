
The basic idea is:

> **Changes must be planned and controlled, and unexpected changes must be reviewed and their consequences addressed.**

---

### 1. Why are changes important for information security?

Changes can introduce new security risks.

For example, an organization decides to replace its existing CRM application with cheaper software.

The change may affect:

- Confidentiality of customer information
    
- Integrity of data during migration
    
- Availability of the CRM system
    
- User access permissions
    
- Authentication mechanisms
    
- Logging and monitoring
    
- Backup and recovery
    
- Integration with other applications
    
- Compliance requirements
    

Therefore, simply asking **"Is the new software cheaper?"** is not enough.

The organization should also ask:

> **"What information-security consequences will this change create?"**

---

## 2. Planned changes

A planned change should be controlled before implementation.

A typical process is:

**Request → Analyze → Assess risks → Approve → Implement → Verify → Close**

### Example: Replacing software

Management decides to replace the company's existing CRM system.

#### Step 1 — Change request

Management proposes:

> Replace the existing CRM with a lower-cost CRM solution.

#### Step 2 — Impact and risk analysis

The IT/security team evaluates:

- What data will be migrated?
    
- How will data be transferred?
    
- Is the new system secure?
    
- Does it support MFA?
    
- Does it provide adequate logging?
    
- Who will have access?
    
- What happens if migration fails?
    
- Can the data be restored?
    
- Does the new supplier meet security requirements?
    

#### Step 3 — Define requirements

The organization determines what must be done to protect information during the change.

For example:

- Encrypt data during migration.
    
- Perform a complete backup before migration.
    
- Restrict administrator access.
    
- Test the new system.
    
- Validate migrated data.
    
- Maintain rollback capability.
    

#### Step 4 — Approval

The responsible authority reviews the analysis and decides whether to approve the change.

#### Step 5 — Implementation

The authorized team performs the migration according to the approved plan.

#### Step 6 — Verification

After implementation, the organization checks:

- Is the system functioning?
    
- Is the data complete?
    
- Is the data accurate?
    
- Are access controls working?
    
- Are logs being generated?
    
- Are security requirements satisfied?

## 3. Unplanned changes

ISO 27001 also recognizes that **not every change can be planned**.

For example:

- Emergency server replacement
    
- Critical security patch
    
- Unexpected network failure
    
- Emergency configuration change
    
- Cyberattack requiring immediate containment
    
- Supplier suddenly becoming unavailable
    

These changes may need to happen immediately.

However, they should still be **analyzed and dealt with afterward** to minimize unwanted consequences.

### Example

A critical vulnerability is discovered in a production server.

The administrator immediately applies an emergency patch without going through the normal change process.

Afterwards, the organization should:

- Record what happened.
    
- Determine why the emergency change was necessary.
    
- Check whether the change caused problems.
    
- Verify that the system remains secure.
    
- Review whether additional actions are required.
    
- Update the change record/process if necessary.

## 4. What should a change management process define?

Although ISO 27001 does not prescribe a specific change-management procedure, a practical procedure can define:

|Area|Question|
|---|---|
|Change initiation|Who can request a change?|
|Change description|What exactly will change?|
|Impact analysis|What systems/processes will be affected?|
|Risk assessment|What security risks could arise?|
|Approval|Who must authorize the change?|
|Implementation|Who will perform the change?|
|Testing|How will the change be tested?|
|Rollback|What happens if the change fails?|
|Verification|How will successful implementation be confirmed?|
|Documentation|What evidence should be retained?|
|Review|What happened after implementation?|

## 5. Change management and risk management

Change management and risk management are closely connected.

For example:

**Change:** Move customer database to a new cloud provider.

⬇️

**Potential risks:**

- Unauthorized access
    
- Data loss
    
- Data leakage
    
- Incorrect permissions
    
- Service interruption
    

⬇️

**Risk treatment:**

- Encryption
    
- MFA
    
- Access control
    
- Backup
    
- Secure migration
    
- Monitoring
    

So, before implementing a significant change, the organization should consider its **information-security risks**.

---

## 6. Change management is not only about IT

This is important.

Changes can occur in:

- Technology
    
- Business processes
    
- Organizational structure
    
- Suppliers
    
- Locations
    
- Personnel
    
- Applications
    
- Infrastructure
    
- Legal/regulatory requirements
    

For example:

> The company acquires another organization.

This could change:

- Users
    
- Systems
    
- Networks
    
- Data
    
- Suppliers
    
- Policies
    
- Access rights
    
- Security responsibilities
    

Therefore, the ISMS should consider the information-security impact of the organizational change.

## 7. Example from your scenario

**Top Management:**  
"We want to replace the existing software to reduce costs."

**IT Administrator:**  
"Before implementation, I'll analyze compatibility, security requirements, data migration, backup, access control, and possible risks."

**IT Head:**  
"Based on the analysis, here is the migration plan, required resources, budget, timeline, security measures, and rollback plan."

**Top Management:**  
"Approved."

**IT Team:**  
"Implements and tests the migration."

**Security/IT Team:**  
"Verifies that the new system meets security requirements."

This demonstrates **controlled change management**.
